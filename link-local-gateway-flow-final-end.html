Kiến trúc & luồng dữ liệu · link-local-private-gateway

VM tới dịch vụ nội bộ đi qua đâu?

Cách service link-local-private-gateway đưa một VM tenant từ địa chỉ metadata 169.254.169.254, qua HAProxy và socat trong container macvlan đứng thẳng trên VLAN 180 (không admin, không netns), tới proxyhub 172.26.8.30:8443 — nơi soi request và phân bổ tới VCR / S3 / MAAS.

VM kaas→ 169.254.169.254:443→ br-int OVS flow→ HAProxy mode tcp→ unix sock→ socat · macvlan v180→ QoS · tc @ host vlan.180→ proxyhub .30:8443→ VCR·S3·MAAS
01

Ý tưởng cốt lõi

OVN đã sẵn có hạ tầng metadata: mỗi network có một namespace ovnmeta-<network_id> chạy HAProxy. Khi VM gửi tới 169.254.169.254, gói vào br-int và bị các OpenFlow do OVN cài chặn lại — khớp đích là IP metadata rồi output tới metadata localport của đúng network đó (interface mang .169 nằm trong namespace). VM không tự chọn được namespace nào. Service này bám lên chính đường ống đó: một custom HAProxy template thêm một listener :443 bên cạnh metadata :80. Nhờ vậy VM có một lối riêng ra các dịch vụ public (VCR/S3/MAAS) qua một proxyhub riêng tư làm trung gian — VM không cần route, không có đường public trực tiếp, chỉ dùng địa chỉ link-local vốn đã có.

Ba tính chất định hình toàn bộ thiết kế:

  • Danh tính không giả được. HAProxy nhét network_id của chính namespace đó vào PROXY-v2 (unique-id). VM không tự đặt được network_id — nó do hạ tầng gán theo namespace VM rơi vào.
  • Passthrough thuần L4. HAProxy chạy mode tcp, không giải mã TLS. TLS đi thẳng end-to-end tới dịch vụ; danh tính đi kèm ngoài luồng (out-of-band) trong header PROXY-v2.
  • Backend cố định. socat chỉ có một đích duy nhất — proxyhub .30:8443. Không có đích động, không exec → không thể biến thành port-forwarder.
02

Các vùng & ranh giới

Sơ đồ dưới đây ưu tiên thể hiện đường dữ liệu và trust boundary. Container gateway dùng macvlan trên VLAN 180, không host-net, không netns/nsenter. QoS/tc nằm trên host parent vlan.180; mũi tên cam nét đứt đánh dấu traffic rời compute node sang mạng dịch vụ.

không tin / rời node nội bộ compute node container macvlan v180 proxyhub (riêng tư) dịch vụ public 🚦 QoS/tc @ host parent vlan.180

🔎 Cận cảnh: OVS (br-int) chặn luồng .169

ovn-controller biên dịch logical flow của OVN thành OpenFlow trên br-int. Hai flow quyết định việc chặn 169.254.169.254 và giao vào namespace — xử lý local trên chassis.

# Khai niem (ovn-controller sinh tu logical flow) - xem thuc te bang: # ovs-ofctl dump-flows br-int | grep 169.254.169.254 table=…, arp, arp_tpa=169.254.169.254 actions=ARP_responder(MAC=metadata-localport) table=…, ip, nw_dst=169.254.169.254 actions=output:<ofport tap trong ovnmeta-<netid>>
  • ARP trước. VM có host-route 169.254.169.254 (DHCP option 121); nó ARP hỏi .169, OVN trả về MAC của metadata localport → VM gửi gói tới đúng MAC đó.
  • Khớp theo IP, không theo cổng. Flow chỉ match nw_dst=.169 → nên :443 (gateway) đi chung đường với :80 (metadata thường). Đây là chỗ custom template "bám" vào.
  • Local-only. metadata localport tồn tại ở mọi chassis và traffic được xử lý nội bộ trên compute node.

03

Chi tiết từng hop

  1. VM gửi tới địa chỉ metadata 169.254.169.254:443

    VM mở kết nối TLS tới 169.254.169.254 — địa chỉ link-local cloud metadata mà mọi VM đều biết. OVN lái gói này vào đúng namespace ovnmeta-<network_id> của network chứa VM (VM không chọn được namespace nào). Cổng :80 vẫn là metadata thường; :443 là listener do custom template thêm.

    TLS ClientHello→dst 169.254.169.254:443

  2. OVS (br-int) chặn .169 và đẩy vào namespace OpenFlow · OVN

    Gói tới 169.254.169.254 không route ra ngoài: khi vào br-int, các OpenFlow do OVN biên dịch & cài khớp đích là IP metadata và output tới metadata localport của network đó — chính là interface mang .169 nằm trong ovnmeta-<netid>. Vì flow khớp theo IP (không theo cổng), traffic :443 cũng được đưa vào ns y như metadata :80 — đó là lý do listener :443 của custom template dùng chung được đúng đường ống metadata sẵn có.

    dst .169 (bất kỳ port)→OpenFlow match→metadata localport → ovnmeta ns

  3. HAProxy nhận, rate-limit, gắn danh tính mode tcp · passthrough

    Listener chạy mode tcp nên không giải mã TLS — chỉ chuyển byte. Trước khi chuyển, nó rate-limit theo IP nguồn (stick-table) và gắn network_id vào định danh kết nối để đẩy xuống backend.

    # custom template render cho tung network (host=169.254.169.254, network_id=<uuid>) listen link_local_private_gateway mode tcp bind 169.254.169.254:443 stick-table type ip size 100k expire 60s store conn_rate(10s),conn_cur tcp-request connection track-sc0 src tcp-request connection reject if { sc0_conn_rate gt 50 } tcp-request connection reject if { sc0_conn_cur gt 30 } unique-id-format <network_id> # danh tinh tenant default_backend link_local_private_gateway_backend
    TLS bytes+network_id gắn vào unique-id

  4. Đẩy vào unix socket kèm PROXY-v2 /link-local-gw/…

    Backend không phải TCP mà là một unix socket trên volume dùng chung với agent. HAProxy ghi send-proxy-v2 — thêm một header nhị phân PROXY-v2 mang unique-id (chính là network_id) đứng trước luồng TLS. Socket 0660 group 42435 nên chỉ HAProxy (uid/gid neutron) mới ghi được — tenant không chạm tới.

    backend link_local_private_gateway_backend mode tcp server link_local_private_gateway unix@/var/lib/neutron/kolla/link-local-gw/link_local_private_gateway send-proxy-v2 proxy-v2-options unique-id
    [PROXY-v2: network_id]+TLS bytes→unix socket

  5. socat trong container macvlan (vlan.180) nối socket ↔ proxyhub

    Container link-local-private-gateway chạy socat không quyền admin (user 42435:42435, cap_add: [], không privileged, không host-net, không netns/nsenter). Phía mạng là một interface macvlan đứng thẳng trên vlan.180 (IP 172.25.180.125/24, gw .1) — đường ra backend mà tenant không có. Mỗi kết nối fork một child (trần max-children=3072). socat chỉ là ống dẫn byte — không đọc, không sửa nội dung — nối socket tới đúng một đích cố định 172.26.8.30:8443. QoS đặt trên host parent vlan.180 bằng tc (htb+fq_codel egress, IFB cho download) — traffic macvlan đi qua qdisc của interface cha nên shape được; shape tổng cả ống, không per-tenant.

    # entrypoint container (khong nsenter, khong cap) — chi mot dich co dinh socat UNIX-LISTEN:/socket/link_local_private_gateway,unlink-early,fork,mode=0660,group=42435,max-children=3072 TCP:172.26.8.30:8443
    unix socket→TCP tới .30:8443 (byte y nguyên)

  6. proxyhub (riêng tư) soi & egress ra dịch vụ public 172.26.8.30:8443

    proxyhub là chốt riêng tư: nhận PROXY-v2, bóc header lấy network_id, kiểm tra request rồi mới egress ra dịch vụ public — VCR (registry), S3 (object store), hoặc MAAS. VM tenant không có đường public trực tiếp; proxyhub là điểm ra public duy nhất. Đây cũng là nơi phân quyền thật sự: mọi quyết định network nào được ra service public nào nằm ở tầng này, không phải ở socat/HAProxy (hai tầng trước chỉ vận chuyển + gắn danh tính).

    [PROXY-v2] + TLS→đọc network_id→VCR / S3 / MAAS
04

Vì sao thiết kế như vậy

danh tính network_id qua PROXY-v2

Không dựa vào src IP (VM có thể spoof). HAProxy trong namespace của network gán network_id — buộc chặt với network VM thực sự thuộc về, không giả được.

bảo mật TLS passthrough

Gateway không giải mã TLS → không thấy nội dung, không giữ khoá. Bí mật chỉ mở tại dịch vụ đích. Đổi lại: rate-limit chỉ ở mức kết nối, không phải mức request.

cô lập container macvlan, không admin

socat chạy user 42435, không cap/không privileged; interface macvlan đứng trên vlan.180 là đường ra backend mà VM không có. Đích cố định nên không thành bàn đạp; đổi lại macvlan bỏ qua netfilter host → cần VLAN 180 sạch + proxyhub authz.

tối giản quyền socket 0660 + group

Socket chỉ HAProxy (gid 42435) ghi được, không world-writable. Tiến trình lạ cùng host không nối thẳng proxyhub để vượt HAProxy được.

06

Yêu cầu ProxyHub — APISIX

Tầng ProxyHub sử dụng APISIX để xử lý traffic ở mức HTTP request. APISIX thực hiện TLS termination, tiếp nhận thông tin từ PROXY Protocol v2, chuyển các thông tin cần thiết thành HTTP header tiêu chuẩn và áp dụng policy riêng cho từng dịch vụ trước khi forward request tới backend.

Các yêu cầu đối với APISIX

Yêu cầu Mô tả
Nhận PROXY Protocol v2 APISIX phải hỗ trợ nhận kết nối sử dụng PROXY Protocol v2 và đọc các thông tin được truyền từ tầng phía trước, bao gồm Client IP và network_id.
Chuyển PROXY-v2 thành HTTP Header Thông tin trong PROXY-v2 phải được chuyển thành HTTP header tiêu chuẩn trước khi forward về backend. network_id được đưa vào X-Network-Id, Client IP được đưa vào X-Client-IP. Backend chỉ cần xử lý HTTP header, không cần hiểu trực tiếp PROXY Protocol v2.
Multisite — mỗi site một bộ APISIX Mỗi site triển khai một bộ APISIX độc lập, ví dụ hcm-ops03, hni-ops04, nhằm tách biệt traffic và giảm phạm vi ảnh hưởng khi xảy ra sự cố tại một site.
Giới hạn theo từng dịch vụ VCR: chỉ cho phép request tới prefix /kaas, các path ngoài phạm vi bị từ chối.

S3: giới hạn bucket theo tenant/network; cấu hình allowlist cần có syntax phù hợp để quản lý policy thông qua Vault.

Luồng xử lý

VM→ PROXY-v2→ APISIX→ Chuyển HTTP Header→ Kiểm tra policy theo dịch vụ→ Backend

APISIX thực hiện:

  • Nhận Client IP từ PROXY Protocol v2.
  • Nhận network_id từ PROXY Protocol v2.
  • Chuyển các thông tin trên thành HTTP header tiêu chuẩn.
  • Route request theo SNI / Host tới đúng dịch vụ.
  • Với VCR, giới hạn HTTP path trong phạm vi /kaas.
  • Với S3, kiểm tra bucket theo allowlist tương ứng với tenant/network.
  • Forward request hợp lệ tới backend.

Vai trò của ProxyHub

ProxyHub/APISIX là L7 Proxy / Policy Enforcement Point nằm trước các dịch vụ backend, thực hiện chuỗi xử lý:

Nhận PROXY-v2→ Xác định Client IP / Network ID→ Chuẩn hóa HTTP Header→ Kiểm tra path / bucket→ Forward tới backend

Các policy áp dụng dựa trên:

network_id Client IP SNI / Host HTTP path S3 bucket

ProxyHub tập trung vào chuẩn hóa thông tin nguồn request, routing và giới hạn phạm vi request theo từng dịch vụ trước khi traffic được chuyển tới VCR, S3, MaaS hoặc các dịch vụ private gateway khác.

Tóm tắt một dòng: VM → 169.254.169.254:443 (HAProxy passthrough + gắn network_id) → unix socket (send-proxy-v2) → socat trong container macvlan không quyền admin trên vlan.180 (đích cố định) → proxyhub riêng tư 172.26.8.30:8443 (bóc network_id, soi request, egress ra dịch vụ public VCR/S3/MAAS). Hai tầng đầu vận chuyển + gán danh tính; proxyhub là điểm kiểm soát ra public duy nhất và là nơi phân quyền thật.
